1 · How we test today

One story, tested by hand, start to finish

Every step below is done by a person, and most of them are repeated every release. The work is careful. The trouble is that it doesn't scale, and a lot of what we know stays in our heads.

Log the bug

Reproduce it, take screenshots, and write the steps, expected and actual results into the tracker.

by hand
5

Retest

When the fix lands, run the case again by hand, then close the ticket.

by hand
6

Regression

Before each release, re-run the old cases to make sure nothing else broke.

every release
7

Report

Count passes, failures and open bugs across sheets and tickets for sign-off.

compiled by hand
Regression grows, the time for it doesn't Each release adds cases to re-run. Something has to give, and it's usually coverage.
Traceability lives in people's heads Which test covers which acceptance criterion, and which bug came from which test, is rarely written down.
Knowledge leaves with people How the app works, which role can do what, where the tricky data is: none of it is recorded anywhere.

2 · How we'll test with the harness

Same steps. Agents do the legwork, you make the calls

Five AI agents on top of a Playwright test suite. Each one stops and asks at the points that need judgment, and none of them files a bug or saves a plan without you.

/test-plannerFetches the story from Jira by its key, reads it with our app notes, flags gaps in the acceptance criteria, designs cases with standard techniques (boundaries, roles, errors). Each case gets an ID linked to its criterion, e.g. PROJ-123-TC001.
/test-generatorPerforms every step in a real browser first, then writes the Playwright test from what actually happened, not from guesses.
test suiteChecks the environment is up, then runs every test, across browsers and roles. Regression is one command.
/test-healerFixes broken tests (selectors, timing) in up to 3 tries. If the app is wrong rather than the test, it says so and explains why.
/defect-raiserCreates the bug in Jira, with steps, expected vs actual and test ID, linked to the story, after checking it isn't already filed. Parks the test until the fix lands; the healer retests it.
cycle reportWritten the moment a run ends: pass rates by priority, criteria coverage, open bugs, and whether each exit criterion was met.

3 · What this means for us

Less repetition, and the judgment stays ours

The harness takes over the repetitive parts: writing up cases, clicking through regression, formatting bug reports, counting results. Deciding what matters stays with us.

Gets easier

  • Regression is a command, not a week. Pick the release and its tickets; it runs them and reports.
  • Bug reports arrive complete: steps, expected vs actual, test ID, story key.
  • Traceability is automatic. A CI check fails any story test that is missing its case ID.
  • Knowledge is written down. Modules, roles, permissions and data are recorded once and kept current.

Stays with us

  • Approving every plan. The planner stops and asks at seven checkpoints.
  • Confirming every bug. Agents never raise one on their own.
  • Exploratory and manual-only testing. Results still get recorded, per case ID.
  • Reviewing agent output the way we'd review a colleague's, and the sign-off call.

Ground rules

  • Every story needs its Jira key. If it's missing, the planner stops and asks.
  • Read-only. Agents never submit forms or change data in the app or database.
  • QA environment only, with dedicated test accounts, never production.
  • Agents never see a password. They start already logged in, and every Jira write asks first.
How we start
1 · Set up once The QA lead connects the harness to our app. An agent walks the app and drafts what it finds, and we correct it.
2 · Pilot one story One real story, end to end. It's a new tool, so this is where we find what needs adjusting.
3 · Roll out Story by story. Existing manual cases carry on alongside, and move over as they're automated.
