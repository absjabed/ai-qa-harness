# QA harness 1.1 — plan

Template maintainers' plan. Not copied into a project's QA repo.

**Why:** a QA team reviewing the harness found two gaps — no agent runs the tests and routes their failures,
and no agent produces a finished, shareable report — and asked for Figma alongside Jira and for a git workflow.
This plan closes those gaps. An independent critique of the first draft cut the parts that added moving pieces
without serving the request; what remains is below.

## What 1.1 adds

| Need | Answer |
|---|---|
| Run tests and route failures | `/playwright-test-executor` |
| A finished, shareable report | `/playwright-test-reporter`, on an extended report script |
| Jira and Figma, connected per member | the existing Jira entry, plus an optional Figma entry |
| A git workflow for QA repos | branches, a story start protocol, commit conventions and `npm run story` |

## Design

### Reporter — `/playwright-test-reporter`

- **Scope** — always asked: one story, several stories, an epic, or a release. The default follows how the
  tests were run: a story run suggests that story's report, a regression run the release's.
- **Format** — always asked: Markdown, HTML, PDF, or several. `QA_REPORT_FORMAT` in `.env` supplies the
  suggested answer. Markdown is always written, as the committed copy; HTML and PDF are rendered from it, PDF
  through Playwright's own Chromium.
- **Numbers come only from the script** (`scripts/lib/cycle.ts`), never from the agent.
- **Script additions** to `npm run report:cycle`: `--epics`, `--by <name>`, `--format md,html,pdf`,
  `--jira <file.json>` (ticket titles and status fetched by the agent), and the release's tickets that have no
  plan yet.
- **Generated by** — `QA_TESTER_NAME`, else `git config user.name`, else the name the agent passes with
  `--by` after asking. The report says which.
- **Name** — `QA-Report_<APP>_<scope>_<release-or-build>_<YYYY-MM-DD-HHMM>`. The timestamp keeps it unique
  across branches.
- **Where** — formal reports are committed in `specs/execution/reports/`; the automatic after-run reports stay
  in the uncommitted `reports/`.
- **Contents** — header (title, scope, release, build, environment and browsers, generated by and when,
  harness version), a summary verdict, totals split automated and manual, pass rate by priority, per ticket its
  Jira title and status, AC coverage and test cases, defects with their Jira keys, tickets with no plan,
  stories not in a release yet, exit criteria, notes, sign-off.
- **Jira** — asked first every time: a test-summary comment on each ticket, and an on-hold note on a blocked
  story. No comments on bugs — the defect-raiser owns those.

### Executor — `/playwright-test-executor`

1. **Asks the selection and the mode, and confirms** — a *story run* (every test of the chosen stories) or a
   *regression run* (the release's stories, or chosen epics or tickets, `@Regression` tests by default). The
   confirmation shows the stories, test count, build and browsers, and waits for a yes.
2. **Runs through the command line**, in the background — `npm run regression -- … --yes` — so the results
   record and the after-run report are written. A very large selection can be split.
3. **Shows the failures grouped** by spec and error, and asks once: heal all, heal these, or stop.
4. **Hands over to the healer** on what failed in that run. Agents hand over through files, not memory: the
   healer reads the run's results, the defect-raiser reads pending defects, the reporter reads the records. A
   session that ends mid-way resumes with the same command.
5. **Offers the defect-raiser** when there are pending defects.
6. **Asks about manual results** when the scope has manual cases still Not Run: enter results now, or leave
   them — the report will show them as not run.
7. **Offers the report**, defaulting to the run's scope.
8. **Offers context-sync suggestions** (below).

The generator, once a story's tests pass review, asks: *run these tests now?*

### Story status — computed, never stored

`npm run story -- status <KEY>` works out where a story is from the real files every time: plan written and
reviewed, tests generated and reviewed, last run, open defects, Jira status, branch. Nothing is stored that
could drift from the files. The reviewer adds one line to the plan when it reviews, so "reviewed" is recorded.

### Context sync — suggestions, applied on a yes

At close-out the executor lists, for the areas the run touched: which test case verified which rule in
`context/<area>.md`, and when; and which known unknowns a test answered. They go to the context-builder's
scoped update and are applied only on a yes. Test results never become new rules.

### Git workflow for a project's QA repo

| Branch | Holds | From | Into |
|---|---|---|---|
| `main` | Tests for what is live | — | — |
| `develop` | Every finished story's tests | `main` | — |
| `release/<x>` | One client release's stories; regression runs here | latest `develop`, at the start of a release cycle | `main` and back into `develop` when the release closes |
| `test/<KEY>-<short-desc>` | One story | the freshly pulled `release/<x>`; `develop` if the story has no release | its base, by pull request |
| `harness/<short-desc>` | Harness changes | `develop` | `develop` |

- **The agent runs git; the QA member answers.** Creating a release branch, pushing and merging always ask
  first. Force-push, hard resets, branch deletion and history rewrites are denied, and the remote's `main`,
  `develop` and `release/*` should be protected.
- **Story start protocol**, before any work on a ticket: a clean working tree, a fetch, an offer to resume an
  existing `test/<KEY>-*` branch, an explicit choice of base branch, a pull of that base (stop if it has
  diverged), then the story branch.
- **A story merges when its tests are generated, reviewed and run** — open defects and `fixme` included, so
  the release branch, its regression and its reports see every open defect. Before merging, the latest release
  branch is pulled into the story's branch, with an offer to re-run if shared files changed.
- **A story with no release yet** branches from and merges into `develop`; the agent says so first, and the
  story is listed as "not in a release yet" in status and reports until it is scheduled.
- **A story moved to another release** with few changes: its plan's Release field is updated, its spec moved
  to the new release's folder, and its commits brought to the new release branch — the agent says how much
  first; a large move stops and asks.
- **Commits** are one line: `<type>(<KEY>): <what> [<stage>]`, typed test-plan, test-review, test-gen,
  test-run, test-heal, defect, test-manual, test-report, context, harness.
- **Records merge cleanly**: union merge for the results CSVs, and one file per defect.
- **Scripts:** `npm run story -- start <KEY> "<desc>"`, `status`, `release-start <x>`.

### Settings, read by key

Agents never open `.env`. `npm run env -- get <KEY>…` answers only from an allow-list of non-secret keys —
`QA_TESTER_NAME`, `QA_REPORT_FORMAT`, `BUILD_UNDER_TEST`, `APP_NAME`, `BASE_URL`, `TRACKER_PROJECT_KEY` — and
always refuses passwords, emails, tokens and database credentials. `.env.example` gains `QA_TESTER_NAME` and
`QA_REPORT_FORMAT`, and `npm run check` fails when code reads a setting `.env.example` does not list.

### MCP

The Jira entry keeps its name, `tracker`, so existing copies keep their guard rails. An optional `figma` entry
is added — the remote server, signed into through the browser; the desktop app's server is offered when it is
installed — with read-only rules. The planner and context-builder use designs as cited design intent; the
reviewer stays independent of them.

## Phases

Each is its own pull request into `main`.

| # | Phase | Done when |
|---|---|---|
| 1 | **Reporter** — the script additions and `/playwright-test-reporter` | Story, epic and release reports on FleetKeep in all three formats, with numbers identical to the script's |
| 2 | **Executor** — `/playwright-test-executor` and the generator's offer | On FleetKeep the planted defect is found, healing is offered once, the bug is raised, the report is written |
| 3 | **Git** — `npm run story`, the protocol, conventions, union merge and one file per defect, guard rails, `npm run env` | A FleetKeep story goes start → run → merged into `release/x`, with no record conflicts |
| 4 | **MCP and context** — the Figma entry and its rules; context-sync suggestions | Figma connects and passes a read check; a FleetKeep run produces sync suggestions |
| 5 | **Docs and release** — every agent list, the walkthrough, the developer guide, `docs/GIT-WORKFLOW.md`, `.env.example` and its check, one worked FleetKeep run, changelog 1.1.0 | `npm run check` passes; a fresh export runs the whole flow |

## Deferred

Flaky-test history, the run-ID helper for test data, guided manual execution, scripted agent checks, and an
upgrade path for existing copies.
