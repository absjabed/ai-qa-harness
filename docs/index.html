Handbook

AI-driven QA test harness

Five agents learn your application, plan, generate, heal, and file defects against a Playwright + TypeScript suite built on the Page Object / Page Factory pattern. Everything project-specific lives in two files — PROJECT-PROFILE.md and .env. Nothing in the agents, the config, or the fixtures names an application.

Setup ≈ 1 hour · Node 18+ · Playwright Test MCP required · database MCP optional but recommended

The pipeline

  1. 00context-builderLearns the application once, so the rest have something to work from.
  2. 01plannerA pasted story becomes a reviewed plan + CSV.
  3. 02generatorDrives the real browser, then writes the spec and any page objects.
  4. 03healerFixes failures, or confirms a genuine bug with you.
  5. 04defect-raiserFiles the CSV row and marks the test fixme.

What makes this different from asking an LLM to write tests

The generator does not write from plan text. It drives the real browser through the Playwright MCP server first, reads back its own action log, and refuses to write a test for any step that has no recorded action. Plan text states intent; only the drive establishes what the DOM actually does.

They stop and ask. The planner has seven mandatory approval checkpoints. The generator blocks on the target file path and on any new page object it is about to create.

They refuse rather than guess. A placeholder still in the profile stops the run. An unregistered module tag stops the run. A missing SQL query stops the run. Each is a point where a guess would produce work that looks right and is wrong.

Two files you edit per project. PROJECT-PROFILE.md — the application, its roles, its vocabulary, its modules, its severity rubric. .env — URLs and credentials. If you find yourself editing something else to make the harness fit, it probably belongs in the profile.

This repo is a template: you copy it per project rather than working in it directly. Setup opens with how to take a copy.

Get running

How the harness learns your application

This repository is separate from the application it tests. It cannot read your source, your database schema or your API contracts — it knows only what someone puts in front of it. Worth understanding before setup, because two of the setup steps exist entirely to answer this.

The five channels

ChannelCarriesWritten by
PROJECT-PROFILE.mdRoles, domain vocabulary, modules, severity rubricYou, from a draft
context/Distilled knowledge: business rules, schema notes, API contracts, state machines, verification queriesThe context-builder, then you
specs/UserFlowsUserRolePermissions/Click-paths per role, permission boundariesThe context-builder, then you
The running applicationWhat the app actually does todayRead live via the Playwright MCP server
The databaseReal schema, real valuesRead via a read-only MCP server, if wired

Per story, add the acceptance criteria you paste in and any screenshots. That is everything. There is no automatic sight of anything else.

Distilled, not dumped

The instinct is to hand the agents a schema dump. That does not work: a real one runs to tens of thousands of lines, and it buries the four facts that matter about a table under ten thousand that do not.

What works is the opposite — explore once, write down the few things that matter, and let that document be the durable knowledge. A context document covers one area of the application: which tables or endpoints are involved, what rules the application enforces on them, how to put the system into a given state, and how to verify it afterwards. That is the difference between an agent that can write a correct database assertion and one that has to ask you for every query.

Why the agents ask you for SQL. They refuse to invent it, because a query written without schema visibility is plausible and wrong. That refusal is correct — but it is a refusal born of blindness. Wire the database MCP server and run the context-builder, and the queries get written down once in context/ instead of being asked for every time.

Record the gaps

context/BASELINE.md ends with a "known unknowns" section, and it is the most useful part of the file. A gap written down makes the other agents stop and ask. A gap filled with a plausible guess makes them confidently wrong, and everything downstream inherits it.

The same applies to the permission matrix: every cell is marked verified or not tested here, and none is filled by symmetry. "The other read-only role could not do this, so this one probably cannot either" is exactly how an assumption becomes a recorded fact.

Provenance, and drift

Every context document records where its knowledge came from, because the sources fail differently:

SourceReliable aboutFails by
Application sourceIntent and rulesGoing silently stale after a refactor
Database introspectionStructureSaying nothing about intent — and misreporting things like nullability
The running applicationCurrent behaviorOnly covering the paths someone actually walked

Context that has drifted is worse than no context, because an agent will act on it confidently. When a test fails because a document no longer matches reality, fix the document in the same change as the test.

Get running

Setup, in ten steps

Get the harness talking to your application, let an agent explore it and draft what it finds, then correct those drafts. Correcting a draft is much faster than writing one cold — which is why step 3 comes before step 4.

First, get a copy. This repository is a template, not a project. You copy it, point the copy at your application, and that copy becomes your project's test suite — the template itself never gains application-specific content.

Recommended: export it into the project's QA repository — an empty folder or a fresh clone. From the template, no install needed:

npm run export -- ../<app>-qa

It copies every file the harness needs, dotfiles included, and leaves behind the three that describe the template — README.md, CHANGELOG.md and the export script. It names the package after the folder, writes a starter README, records the template version and commit in PROJECT-PROFILE.md section 1, and runs check:docs against the copy. It never overwrites: if the target already has any of its files, it lists them and writes nothing.

Copying by hand? Take every file git ls-files lists except those three — none of the rest is optional. The one never to miss is .gitignore: without it, .env and its passwords are committed on the first push. Then do what the export would: rename name in package.json (while it reads ai-qa-harness, check:docs treats the copy as the template and fails on your application's name), and record the template version and commit in profile section 1. SETUP.md step 0 has the full list, and the GitHub-template route.

Recording the version and commit is what lets you tell later whether a difference is yours or just the template having moved on. The template's changelog marks each entry Adopt, Optional or New copies only, so you can tell what is worth pulling into an existing copy.

Improvements you make while working on a project come back upstream only if they are application-agnostic — a sharper agent prompt, a new BasePage helper, a better error message. Anything that names your application stays in your copy. That line is what keeps the template reusable, and it erodes quietly if nobody holds it.

  2. 2

    Connect it to your application

    Two files, both needed before an agent can do anything useful.

    cp .env.example .env
cp .mcp.json.example .mcp.json

    In .env, the minimum to get moving: APP_NAME, TRACKER_PROJECT_KEY, BASE_URL, and one <ROLE>_EMAIL/<ROLE>_PASSWORD pair per role. The var name is the role key uppercased, split on the camelCase boundary: caseWorker → CASE_WORKER_EMAIL. Set the roles array in config/projectProfile.ts to match.

    In .mcp.json, the Playwright entry is required — the context-builder, generator and healer cannot work without a browser. The database entry is optional and removes the single biggest source of friction here: with it, agents read your schema instead of asking you for every query.

    Use a read-only database account, against QA. An agent with write access is one confused instruction away from changing data other people's tests depend on, and there is no undo. Read-only removes the possibility rather than relying on judgment. Never point it at production.

    Wired a database server? Name its tools too. In Claude Code the tools: line in an agent's wrapper is an allow-list, and a connected server's tools are withheld from any agent that does not name them. Two agents use the database, so append its tool names to the tools: line of both .claude/commands/playwright-context-builder.md (to introspect the schema) and .claude/commands/playwright-test-healer.md (to judge a failing database-backed assertion).

    Names take the form mcp__<server>__<tool> — mcp__database__<tool> with the example's server key. /mcp in an interactive Claude Code session lists what your server exposes. Name only read-only tools, so read-only holds even if the account turns out not to be.

    Skip it and nothing errors — both agents quietly behave as though no database existed. This is frontmatter wiring, not instructions, so it is the one wrapper edit that is expected.

    If you are not using Claude Code

    The harness does not require it. The test suite uses no AI at all, the knowledge layer is plain markdown, and the agent definitions live in agents/ as plain prose with no vendor's frontmatter and no vendor's tool names. Only the wrappers in .claude/ are Claude-specific, and each is a single line pointing at its canonical file.

    To add another tool: put a one-line wrapper where that tool looks for agent definitions, translate the frontmatter, and point it at the same MCP servers — the protocol is open, only the config file's shape differs. agents/README.md has the locations and the tool-name translation table.

    Whichever tool you use, edit agents/*.md, never a wrapper — a wrapper that grows instructions of its own is a second copy waiting to drift. And note that porting is the easy part: these definitions depend on blocking checkpoints, refusals and self-audits, and a weaker model drops those first. Match the model intent, not just the syntax.

    Baseline the application

    /playwright-context-builder

    This is the step that answers "how does a separate repository learn anything about my application". It asks what sources exist, walks the app as each role, reads whatever local sources you point it at, introspects the database if one is wired, and writes context/BASELINE.md plus drafts of the profile sections, the navigation plans and the module tags.

    With only a URL and credentials it can still map modules, navigation and permissions by walking the application — that alone is most of the value. Everything else widens what it can establish.

    Before you run it

    It asks about most of this at its first checkpoint, but a run started without it stalls there or comes back thin.

    What to have ready
    Must have The application reachable from where the agent runs — VPN or allow-listed IP if needed, and not mid-deploy.
    BASE_URL and a working <ROLE>_EMAIL/_PASSWORD pair per role in .env — log in by hand as each first.
    The role keys in config/projectProfile.ts and the Role key column of profile section 2, with the baseline role named. It logs in as each role listed there and drafts the rest of the row, but cannot guess which accounts exist.
    The Playwright MCP server connected (/mcp), browsers installed.
    Worth gathering A read-only QA database account, wired in .mcp.json with its tools named in the wrapper (step 2).
    Local paths to the application source, an OpenAPI or Swagger file, schema scripts, integration contracts, exported requirement or wiki pages — it asks for each and checks it can read it.
    Who to ask about which area.
    Decide Which environment — QA or staging, never production. It roams read-only, but the environment is shared, so tell the people testing in it.
    What it should stay out of — anything out of scope, or where even opening a screen has an effect. Tell it at the first checkpoint.
    That you will be there: it stops at every checkpoint and waits.

    Use dedicated test accounts. To log in, the agent reads each password from .env and types it into the browser, so the value passes through the AI conversation. Use QA-only accounts that exist for testing — never a person's own account, and never one that also works in production.

    Skipping is allowed: write the profile and flow plans by hand instead. Same work, no first draft.

  4. 4

    Review and finish the project profile

    Go through all eleven sections of PROJECT-PROFILE.md, correcting what step 3 drafted and filling what it could not know.

    • Section 2 (Roles) — the planner uses this to decide which roles a story implicates. Name the baseline full-access role explicitly.
    • Section 3 (Vocabulary) — the entities the planner is forbidden to inline. Anything missing here ends up hardcoded in a test.
    • Section 7 (Severity rubric) — your own quality plan's wording. The healer classifies every confirmed defect against it.
    • Section 9 (Knowledge sources) — what the agents can and cannot reach. Keep it honest.
    • Section 10 (Test strategy) — test types in scope, and the entry and exit criteria npm run report:cycle judges a cycle against.
    • Section 1's issue key format — every story must arrive with its key, and the agents validate against it. Tighten storyKeyPattern in config/projectProfile.ts to match.

    npx playwright test tests/example.spec.ts --grep "@Priority1"

    That passing means login and the dashboard are wired. It's the milestone worth stopping at — everything after builds on it.

Planner and generator both read them before tracing a flow through pages/ themselves, and the healer checks them before calling a blocked action a defect. Get running

Your first real test

  1. Paste the story, with its issue key, into the conversation, then run /playwright-test-planner. No key, and it stops to ask. Work its checkpoints. Out: specs/<KEY>.plan.md and .plan.csv.
  2. Read the plan's gap table — "new page objects, fixtures and data keys required". If a data key is listed, add it to data/testData.ts yourself; the generator flags data keys but doesn't author them.
  3. Generate with /playwright-test-generator. It drives the browser, then stops twice: for the target file path, and for each new page object.
  4. Run the spec.
  5. Heal what fails with /playwright-test-healer.
  6. File confirmed defects with /playwright-defect-raiser.
  7. Close the cycle with npm run report:cycle.

Checkpoint 4 is the cheapest redirect in the pipeline. The planner shows you scenario titles only, before any scenario is written out. Trimming there costs a sentence; trimming at the full-plan checkpoint means re-reviewing everything.

Reference

The five agents

Think of them as five roles on a QA team: someone who learns the product, an analyst who plans, an engineer who automates, an engineer who triages failures, and an administrator who files the paperwork. Each hands off to the next, but each also works alone and reads its input from disk — a plan reviewed on Monday generates fine on Wednesday.

You are the sixth role, and not an optional one. The first three stop and ask for your approval at every decision that would be expensive to get wrong; the fourth asks before calling anything a defect. None of them is designed to be left running unattended — except the last, which makes no judgments at all.

/playwright-context-builder an application → what the harness knows about it
opus · effort xhigh needs Playwright MCP database MCP optional writes context/ + drafts profile & flow plans

The role it plays: the new team member who spends their first week learning the product. It asks what documentation and access exist, logs in as each role and walks the application, reads whatever you point it at, and writes down what it found — including, and this is the part that matters, what it could not establish.

What it needs first

The application reachable, a working credential pair per role in .env, the role keys in the profile, and the Playwright MCP server connected. Database access and local sources are optional extras; with a database, its tools must be named in this agent's wrapper. Setup step 3 has the full list — including why these should be dedicated test accounts.

When to run it

Not for every story. It runs once at setup, before filling in the profile by hand — it drafts most of that for you. Day-to-day testing never calls it: each story goes planner → generator → suite → healer → defect-raiser, and those agents read what it wrote.

WhenWhat runs
Project setup — once/playwright-context-builder
Every story or testing taskplanner → generator → run the suite → healer, if something fails → defect-raiser
Occasionally, when knowledge goes stale/playwright-context-builder again — usually for one area

Run it again when the application gains a module or a role, when a release changes navigation or permissions, when database access becomes available having previously been absent — or when the other agents keep asking about one area, its SQL or where a screen is, which means context/ does not cover it.

Name the area, module or role and it runs for that alone, leaving the rest of the baseline untouched. A re-run is an update, not a fresh start: it keeps what people corrected and shows differences before overwriting anything. Usually the QA lead or harness owner runs it, not every tester.

What it produces

OutputWhat it carries
context/BASELINE.mdWhich sources exist and are reachable, the module map, roles and authority, domain vocabulary, APIs, data-layer facts — and known unknowns
context/<area>.mdPer area: schema quick reference, the invariants the app enforces, states and transitions, setup recipes, verification queries
Draft PROJECT-PROFILE.md §2–4Roles, vocabulary, modules — for you to correct
Draft navigation plansOne per role, plus the cross-role permission matrix
Draft module tag tableIn specs/RegressionTags/

How it gathers

  1. Inventory — it asks what exists and what is reachable. It cannot detect most of this, and rows routinely move from "yes" to "no" once someone checks.
  2. Roam — logs in as each role and walks the application read-only, mapping modules, entry paths, and what is visibly absent for one role compared with another. That absence is the permission boundary.
  3. Read — whatever local sources you confirmed: application source (for validation rules, enum values, state machines), API documentation, contracts, requirement docs.
  4. Introspect — the database, read-only, if a server is wired.
  5. Distil — into the documents above, each with its provenance and date.

What it will not do

  • Write anything, anywhere. No forms submitted, no records created, no settings changed, no INSERT/UPDATE/DELETE. It is mapping an environment other people are testing in, and a stray write is someone else's failing test tomorrow.
  • Infer a business rule from a screen label.
  • Fill a permission cell by symmetry. "The other read-only role could not do this either" is how an assumption becomes a recorded fact.
  • Trust introspection blindly. Schema tools misreport things like nullability; anything surprising gets confirmed with a direct query, and the document says that it was.
  • Overwrite what a person wrote without showing the difference first.

Its "known unknowns" section is the deliverable, not the leftovers. A gap recorded there makes the other agents stop and ask you. A gap filled with something plausible makes them confidently wrong. If that section comes back empty after a first pass over a real application, it has not been honest.

/playwright-test-planner story → reviewed test plan
opus · effort xhigh no browser 7 checkpoints writes specs/*.plan.md + .csv

The role it plays: the senior test analyst who reads a story properly. It works out which roles the change touches, which scenarios are worth writing, and which are low-value permutations — then walks you through its thinking in stages and waits for your sign-off before anything is written down. It writes no test code at all.

How to invoke

Paste the story into the conversation — key, title, description, AC as plain text — then run the command. No tracker API. Screenshots are supplementary: used for field names, layout and labels the text omitted, never to invent behavior they only imply.

Story key and test case IDs

The story's issue key is mandatory — without one the planner stops and asks before doing anything else; with one that doesn't match the configured format, it asks you to confirm. It is the only agent that assigns TCIDs, <STORY-KEY>-TC<NNN>, and it keeps them stable: revising a plan preserves every existing ID and marks dropped cases Retired. On saving, it seeds a Not Run row in specs/execution/manual-results.csv for each manual case, so none is forgotten at closure.

How it assigns priority

Four questions, in order, stopping at the first yes — so priority isn't assigned by vibe:

  1. Failure corrupts/loses data, or blocks a role from a core action with no workaround? → P1
  2. The only coverage for its AC, so cutting it leaves that AC untested? → P1
  3. Replicates a covered P1 for a secondary role, or a secondary flow with a workaround? → P2
  4. Otherwise — cosmetic, rare, low blast radius → P3

Ties round toward P3, unless skipping would leave a data-integrity or core-flow gap uncovered elsewhere.

The completeness critique

After drafting, it re-reads its own scenario set as a skeptic: which implicated role has no scenario, which page variant was skipped, which technique fits an AC but wasn't applied, which cross-feature interaction was never asked about. A different failure mode from the self-audit — that only catches gaps against ACs already named.

What it will not do

  • Invent a story key
  • Guess a selector for an element with no page object
  • Name a data key that doesn't exist
  • Dictate which spec file a scenario lands in — that's the generator's checkpoint
/playwright-test-generator plan → spec + page objects
opus requires Playwright Test MCP 2 blocking checkpoints writes tests/ + pages/ + lib/BaseTest.ts

The role it plays: the automation engineer who actually opens the application. It clicks through each step of the approved plan in a real browser to find out how the page really behaves, then writes that up in your suite's conventions — reusing existing page objects where they fit and building new ones where they don't. It will not write a line for a step it never performed.

The loop, per step

  1. generator_setup_page — mandatory, even when the plan reads descriptive enough to write code directly.
  2. Drive the step live. This drive is exploratory — it operates on the raw page to discover real behavior, and is not the shape the final code takes.
  3. Map it back to conventions: which page object method (I1), which fixture (I2), which data key (I3/I4). Scope ambiguous locators now (I7), at the point the locator is written.
  4. generator_read_log — confirm a real recorded action exists for every step. Empty or partial log means the drive didn't happen: it stops and re-runs rather than writing.

Two blocking checkpoints

Target file path. It will not assume a path from the scenario name, even when one seems obvious. It asks for release and story key, assembles the path per profile section 8, and confirms the folder exists — generator_write_test can't create parent folders.

New page objects. Before implementing it tells you which file it's about to touch and waits — "this page already exists, I'm going to implement addRecord on RecordListPage.ts".

What to expect in the output

  • Title = TCID + the plan's summary, verbatim — test('PROJ-1234-TC004 Validate that…', …) — so a failure traces back to its plan row
  • One test per TCID, in tests/stories/<release>/<STORY-KEY>.spec.ts
  • import test from '@lib/BaseTest', expect from @playwright/test
  • Every plan step wrapped in its own test.step(...)
  • test.beforeEach calling userLogin for anything authenticated
  • Tags: P1 → ['@Regression','@Priority1','@Module'] · P2 → @Priority2 variant · P3 → ['@Priority3','@Module'], no @Regression
  • Any new page object wired into lib/BaseTest.ts — implemented, not left as a comment

What it will not do

  • Mint a TCID — a scenario with no plan row goes back to the plan first
  • Write a test for a step it never drove
  • Assume a file path
  • Invent a module tag — it asks, then writes the row into regression-tags.md itself
  • Invent SQL
  • Write a role name into a describe title as a substitute for a tag
/playwright-test-healer failing tests → fixes, or a confirmed defect
opus requires Playwright Test MCP database MCP optional 3 attempts per test writes specs/temp-defects/defect-log.json

The role it plays: the engineer who triages a red build. It runs the failures, reproduces them, and works out whether the test is wrong or the application is. Most failures are the test's fault — a moved button, a race, stale data — and it fixes those itself. When it believes the application is genuinely broken it stops, shows you the evidence, and asks you to confirm before anything is recorded as a defect.

The three-attempt rule

Up to 3 fix attempts per test, then one of three things:

  • Passes → done.
  • High confidence it's a real bug → stops immediately, even mid-attempt, and runs the Defect Confirmation Workflow.
  • Still failing, criteria not met → stops, summarizes what it tried and what it still suspects, asks. It won't guess "bug", and won't retry past 3.

Ruled out before calling something a bug

  • A selector that changed and can be updated
  • A timing issue fixable with a proper wait
  • An ambiguous locator matching a different element than intended (I7)
  • Stale test data or an incorrect assumption
  • Flakiness — reproduced at least twice
  • A documented permission boundary — it checks the navigation plans first

Database-backed failures — it depends on access

DB queries run in the Node process, not the browser, so no browser tool can see what the database holds. Whether the healer can see it itself depends on whether the project wired a read-only database MCP server. The two paths reach different conclusions, so it says which one it is in.

With database access, it re-runs the assertion's own query — read-only, SELECT only — and reads the result:

What it findsConclusion
The value is now what the test expectedTiming. The assertion ran before the app finished persisting — fix with a wait, not a defect
Wrong, and contradicts an invariant in context/Strong evidence of a real bug → defect workflow
Wrong, and nothing documents what it should beUnresolved. Reports both values and says what it cannot distinguish
The row is missing entirelyUsually stale or unseeded data — asks about reseeding

Without database access, it declines to guess. It cannot distinguish an application bug from stale data or a timing problem, and those have completely different fixes — so it stops and reports which assertion failed, the query involved, and that it cannot verify the database's state.

This is the one place the harness deliberately declines to reach a conclusion — and the one place wiring the optional database MCP server changes what an agent can do rather than just how fast it does it. Two cautions even with access: introspection tools misreport structure, so confirm anything structural against real rows; and one query shows the state now, not at assertion time.

In Claude Code, "wired" means named too: the database's tools must be on the healer wrapper's tools: line, or it behaves as though there were none. Setup step 2 covers it.

It never changes a TCID

A fix may reword a title's summary; the <STORY-KEY>-TC<NNN> prefix stays exactly as it was. A failing test with no TCID is reported as a suite defect, not logged against the application.

Retesting fixed defects

Asked to retest, it switches each test.fixme( back to test( and runs it twice. Passes both → active again, log entry marked verified. Fails either → the fixme is restored exactly and the entry stays raised.

Defect Confirmation Workflow

The single exception to "don't ask questions". It presents the test, the violated expected-result line, observed behavior, evidence ruling out a test-side cause, and a severity classified against profile section 7 — judged by observed impact, never by the test's @PriorityN tag, which is coverage priority, not defect impact.

On your confirmation it appends to the defect log. It does not write the CSV and does not mark the test fixme(). The test stays red until the defect-raiser runs.

/playwright-defect-raiser defect log → tracker CSV + fixme
opus no browser unattended — asks nothing writes specs/defects.csv

The role it plays: the administrator who does the paperwork. Every judgment was already made and confirmed by a person; this agent only turns it into a properly formatted bug row and marks the failing test as a known issue so it stops breaking the build. It asks nothing and decides nothing — if an entry looks wrong, it stops and tells you rather than filing something approximate.

Traceability it adds

Every filed row carries the story key and TCID, in its labels and a Traceability line, so the tracker leads back to the test case and its acceptance criterion. An entry it can't trace is left pending and reported rather than filed.

Per pending entry

  1. Map severity to tracker columns via profile section 7. Default: P1 Highest/Critical · P2 High/Major · P3 Medium/Minor · P4 Low/Low.
  2. Append a row to specs/defects.csv.
  3. Find the test() whose title matches exactly, change to test.fixme(, add a comment referencing the defect and what the app does instead.
  4. Set status: "raised", add raisedAt.

How it covers the testing lifecycle

The software testing life cycle runs from reading a requirement to closing a test cycle. Each phase has a home in this harness — and one thread, the test case ID, runs through all of them so that a failure at the end can always be traced back to the requirement at the start.

Phase by phase

PhaseWhat covers itWhat it produces
Requirement analysisplaywright-context-builder; the planner's first checkpoint, which must flag ambiguous or missing acceptance criteriacontext/BASELINE.md; each plan's AC traceability table
Test planningPROJECT-PROFILE.md section 10 — the test types in scope, and the entry and exit criteriaA strategy every story's test design serves
Test case designplaywright-test-planner — equivalence partitioning, boundary values, decision tables, state transitions, pairwise, error guessingspecs/<KEY>.plan.md and .plan.csv, one TCID per case
Environment setup.env, .mcp.json, and the readiness check in lib/globalSetup.ts; data/seed.ts for a known data stateAn environment verified reachable before any test runs
Test executionPlaywright, with playwright-test-generator automating each case against the live app and playwright-test-healer triaging failures; manual cases recorded in specs/execution/test-results/results.json, manual-results.csv
Defect managementHealer confirms with a person → playwright-defect-raiser files it → the healer retests once fixedspecs/defects.csv for the tracker; a defect log with each defect's status

A note on naming: STLC test planning is strategy — what gets tested and when a cycle can start or finish. The agent called planner does test design, one story at a time. The strategy lives in the profile; the planner works within it.

The thread: traceability

Five things, joined by an ID that appears on both sides of each link:

  1. ACAcceptance criterionOne testable statement in the story — AC2.
  2. TCTest caseA plan row — PROJ-1234-TC004. Linked to its AC in the plan's table.
  3. TESTAutomated testIts title starts with the TCID.
  4. RESULTResultPlaywright records it by title.
  5. DEFECTDefectCarries the TCID and story key.

Walked forward, the chain answers "is this requirement covered, and does it work?" Walked backward, it answers "what does this bug actually break?" — a failing test leads to its test case, to the acceptance criterion, to the story. That backward walk is what turns a red test into a sentence a product owner understands.

The rules that keep it intact

  • Every story needs its issue key — a Jira key, for example, in the format set in profile section 1. The planner stops and asks when one is missing. There is no key-less mode.
  • TCIDs are <STORY-KEY>-TC<NNN>, assigned only by the planner, sequential from 001.
  • They never change. A revised plan keeps every existing TCID, gives new cases the next unused number, and marks dropped ones Retired. A number is never reused.
  • Every story test's title starts with its TCID: test('PROJ-1234-TC004 Validate that an expired reset link is rejected', …). The generator writes them that way; the healer never alters the prefix.
  • Every defect records its TCID and story key, and a defect that can't be traced is not filed.

This is invariant I8, and npm run check:trace enforces the mechanical parts on every push: TCIDs well-formed and unique, every story test titled with one, every one present in its plan and not retired.

Entry and exit criteria

Entry — the application answers at BASE_URL, and the database if in scope. lib/globalSetup.ts checks both before every run, so a down environment produces one clear message instead of a report full of failures unrelated to the tests. The rest — stories keyed with AC, plans approved, data seeded — are listed in profile section 10 for the team to confirm.

Exit — thresholds in profile section 10, mirrored in config/projectProfile.ts:

CriterionDefault

A defect's life

The retest matters more than it looks. Without it a fixme'd test stays skipped long after its bug was fixed, and the suite quietly loses coverage nobody notices is gone.

Closing a cycle

npm run report:cycle

Reads the plans, the latest run, the manual results and the defect log, and writes reports/cycle-summary-<date>.md: every test case's outcome — Passed, Flaky, Failed, Blocked by a known defect, Skipped, or Not Run — pass rates by priority, acceptance-criteria coverage per story, open defects, traceability gaps, and each exit criterion marked met or not.

It reports; it does not decide. Closing a cycle is a person's call, and a criterion missed knowingly — with the reason written down — is a legitimate outcome. --strict exits non-zero when a criterion is unmet, for teams that want the report to gate a pipeline.

What is still out of scope

  • Performance, load and security testing. Use dedicated tools; this harness is functional testing through the UI, database and API. Accessibility is covered, optionally, by BasePage.expectNoAccessibilityViolations() — automated checks find roughly a third of accessibility problems, so a pass means "no obvious barriers", not "accessible".
  • Tracker sync. Defects leave as a CSV for import; nothing reads ticket status back. The tracker's key is recorded in the defect log by hand.
  • Change-impact analysis. Tags select what to run; nothing maps a code change to the tests it affects.
  • Test data content. The seeding mechanism exists; what to seed is yours to write.
  • Manual execution tooling. Manual results are a CSV, not a test-management tool.
  • Real-world proof. None of this has yet run end to end against a live application.

Reference

Invariants I1–I8

The conventions every test follows. They live in one file, TEST-AUTHORING-INVARIANTS.md, cited by number from three agents — so a convention has exactly one place to change.

I1
Page Object Model

Every UI interaction is a method on a page object. No raw locator in a spec file. Locators are readonly properties initialized in the constructor — never built inline in a method body, where they're invisible to anyone auditing what the page depends on.

I2
Page Factory fixtures

import test from '@lib/BaseTest', expect separately. Destructure only what you need. Never new SomePage(page) — one construction site per page object means a constructor change is one line, not a grep.

I3
Centralized test data and SQL

No literal business value in a test or plan — reference a data/testData.ts key. No inline SQL — reference a sqlQueries.<key>, executed inside a page object method. The agents don't invent SQL; they have no schema visibility, so a query they wrote would be plausible and wrong.

I4
Credentials

Only testUsers.<role> / defaultUsers.<role>, driven through userLogin in a beforeEach. Never a literal, not even as an example. Values live in .env.

I5
No hardcoded assertion values

Counts, statuses, dates and list contents that vary by environment get asserted via pattern, set-membership, or a before/after comparison against a runtime value — never a number copied out of a manual exploration run.

I6
Environment-driven config

URLs and DB settings come from .env via appConfig. Never a literal environment URL, hostname, or credential anywhere in the repo.

I7
Locator uniqueness

Anything that could match several elements gets scoped to one. An ambiguous locator that happens to work during an exploratory drive is exactly what produces a flaky test weeks later — scope it at authoring time, not after a healer pass finds it.

I8
Traceability

Every story needs its issue key — ask when it is missing, never invent one. TCIDs are <STORY-KEY>-TC<NNN>, assigned only in the plan and never renumbered or reused. Every story test's title starts with its TCID; defects carry it too. npm run check:trace enforces the mechanical parts.

Reference

Components, explained

Nothing here is clever, but the pieces only make sense in relation to each other. So first: what actually happens when one test runs, and which file does what along the way.

Follow one test through the harness

  1. Playwright starts, reads playwright.config.ts, which loads .env and decides which browsers to run in.
  2. Before any test runs, lib/globalSetup.ts checks the application answers at BASE_URL — and the database, if in scope — and seeds test data if SEED_TEST_DATA=true. If the environment is down, the run stops here with one clear message, rather than every test failing for a reason that has nothing to do with it.
  3. The spec file imports test from lib/BaseTest.ts. It asks for the page objects it needs by name — { loginPage, dashboardPage } — and gets them constructed and ready.
  4. beforeEach calls userLogin, which asks data/auth_data.ts for a role's credentials. Those are read from .env at that moment — they exist nowhere in the code.
  5. userLogin drives pages/LoginPage.ts to sign in, then asks pages/DashboardPage.ts to confirm the session really started.
  6. Each test.step calls a method on a page object. The spec never touches a selector — the page object owns those, so when the markup changes there is one file to fix.
  7. A value the test needs — an account number, a status, a boundary — comes from a named key in data/testData.ts, never typed into the test.
  8. If the test checks the database, the page object fetches the query from data/sql_queries.ts and runs it through config/DbConnection.ts, then compares that against what the screen showed.
  9. The test's title begins with its TCID — PROJ-1234-TC004 Validate that… — so its result, and any defect raised against it, leads back to the plan row and the acceptance criterion it verifies.
  10. The tags on the test — @Regression, @Priority1, a module tag — decide whether it ran at all under a filtered --grep.

The through-line: a spec file says what is being checked, in business terms. Everything else — how to find an element, what a valid account number is, how to reach the database — lives somewhere a person can find without reading the test. That separation is what the eight invariants exist to protect.

Knowledge — what the harness knows about your app

context/you fill this in

Everything the harness knows about your application that isn't in the profile.

BASELINE.md is the inventory: which sources exist and are reachable, the module map, each role's authority, the domain vocabulary, the data layer — and a known-unknowns section that is the most useful part of the file. Alongside it, one document per area of the application carrying its business rules, its states and transitions, and the queries that verify them.

Distilled, never dumped. A schema dump buries the four facts that matter about a table under ten thousand that don't.

You touch it: the context-builder writes the first pass; you correct it, and you fix a document in the same change as any test that failed because it drifted.

.mcp.jsonyou fill this in

How agents reach the browser and, optionally, the database.

The Playwright entry is required — three of the five agents cannot work without a browser. The database entry is optional and is the single biggest reduction in friction available: with it, agents read your schema instead of asking you for every query. Use a read-only account against QA — and in Claude Code, name its tools in the context-builder and healer wrappers (setup step 2).

You touch it: once at setup, from .mcp.json.example. It is gitignored — it usually carries a connection string.

Configuration — how the harness is wired

PROJECT-PROFILE.mdyou fill this in

A briefing document about your application, written for the AI agents.

Eleven sections: what the app is, who can log into it, what its business entities are called, what its feature areas are, whether it has a database and an API, how your team rates defect severity, where test files go, what the agents can and cannot reach, the test strategy — scope, entry and exit criteria — and a setup checklist. Section 1 also fixes the issue-key format every story must carry.

You touch it: once at setup, then whenever the application gains a role, a module, or a new domain term. Every agent reads it before doing anything.

config/projectProfile.tsyou fill this in

The same briefing, in a form the code can read.

Three things. The list of role names — typed, so a misspelled role is caught when the project compiles rather than when a test runs at midnight. The pattern every story key must match, which npm run check:trace validates TCIDs against. And the exit-criteria thresholds from profile section 10, which npm run report:cycle evaluates.

You touch it: at setup, whenever you add a role, and whenever your exit criteria change.

config/testConfig.tsrarely edited

Everything that differs between QA, UAT and local — in one place, read from .env.

The application URL and the database settings live here. Ask it for the base URL when BASE_URL is not set and it raises an error instead of guessing a default. That is deliberate: a harness that quietly falls back to some default address will happily test the wrong system and report all green.

You touch it: only to add a new environment setting — and add it to .env.example at the same time.

config/DbConnection.tsrarely edited

How tests read the database, and how they report it when they cannot.

Two behaviors worth knowing. It checks your database settings are filled in before dialling, so a missing .env reads as "you have not configured this" instead of a connection stack trace that looks like an outage. And when the server refuses for a reason that will not fix itself — a firewall that does not know your IP, a wrong password — it remembers, so the rest of the run fails instantly instead of waiting out a full timeout on every single test.

You touch it: only if your project uses something other than SQL Server.

playwright.config.tsrarely edited

How the tests are run: which browsers, how long to wait, what to capture on failure.

Three run configurations — Chromium, Edge, and an API one that launches no browser at all. Tests run one at a time by default, because they share the same test data; running them in parallel before each test owns its own data produces failures nobody can reproduce.

You touch it: to add a browser, or to delete the API configuration if your project has no API.

Data — the values tests use

data/auth_data.tsreads .env

Who the tests log in as.

It holds no passwords. Ask it for a role and it fetches that role's credentials from .env at that moment. A role nobody configured only causes an error if a test actually tries to use it — so a suite covering two roles is not blocked by the three it never touches.

You touch it: almost never. You add roles in .env and projectProfile.ts; this file follows automatically.

data/testData.tsyou fill this in

Every business value a test needs, each under a name.

An account number that exists, one that does not, one that is malformed, one that has been closed — those four cases cover most of what good test design asks for. Also the application's real limits (field lengths, page sizes) for boundary tests, and a set of awkward inputs (empty, very long, unicode, special characters) for the error-guessing ones.

You touch it: at setup, and every time a test needs a value that is not there yet. Adding a key here is what stops that value being typed into a test.

data/sql_queries.tsyou fill this in

Every database query the suite runs, each under a name.

Keeping them together means a schema change has one place to be fixed, and a reviewer can see the whole database surface the tests depend on in a single read. The agents will add queries here when asked, but they never write the SQL themselves — they cannot see your schema, so anything they invented would look plausible and be wrong.

You touch it: whenever a test needs to verify something against the database.

Page objects — how tests talk to screens

lib/BaseTest.tsyou extend this

The switchboard: a test asks for a screen by name, and gets it ready to use.

Instead of every test building its own copy of a page object, each one is registered here once. A test writes async ({ dashboardPage }) => and it arrives. Two benefits: a change to how a page object is built is one edit rather than a hundred, and you can see a test's dependencies in its first line.

You touch it: every time you add a page object — three small edits: import it, list it, register it.

pages/BasePage.tsshared behavior

The things every screen needs, written once.

Navigating to a page, waiting for something to appear properly (rather than sleeping for a fixed number of seconds and hoping), reading a table column into a list, comparing what the screen shows against what the database returned, narrowing a selector that would otherwise match several elements, and checking a page for accessibility violations — optional, and a pass means "no obvious barriers", not "accessible".

You touch it: when you find yourself writing the same helper on a third page object — but only if it genuinely applies to any screen.

pages/LoginPage.ts · pages/DashboardPage.tspoint these at your app

Two working examples, already connected to everything else.

They ship with placeholder selectors. Replace those with your application's real ones and the login flow, the example test and the whole fixture chain start working. DashboardPage also carries the reference example of checking the screen against the database — copy its shape when you write your own.

You touch it: at setup, step 4. This is the moment the harness becomes your harness.

pages/common/shared widgets

Parts of the interface that are not any one screen.

The sign-out menu, the shared login helper, and anything else reachable from everywhere — a nav bar, a global search, a notification tray. Screen-specific page objects live one level up in pages/.

You touch it: when a widget appears on more than one screen.

Workflows

Condensed. Full recipes — including adding page objects and DB assertions by hand, and starting a new project from the template — in WORKFLOWS.md.

A test that passed last week now fails

Decide first whether the application changed or the environment did. They look identical from a red test and have completely different fixes.

npm run db:check

Unreachable → environment. Fix that before touching any test. Then run the healer and expect one of four outcomes:

OutcomeMeans
Fixed in ≤3 attemptsSelector drift, timing, or an ambiguous locator
Asks you to confirm a defectApp behavior genuinely contradicts an expected-result line
"Cannot verify database state"A DB-backed assertion it can't adjudicate — you run the query
Stops after 3, lists suspicionsDoesn't meet bug criteria and isn't an obvious test fix

Adding a page object by hand

Often faster than a full generate for a small screen. Three moves: create the file extending BasePage, wire it into lib/BaseTest.ts (import, Fixtures field, factory), destructure the fixture in a test.

export default class RecordListPage extends BasePage {
    readonly rows: Locator;

    constructor(page: Page) {
        super(page);
        this.rows = page.getByRole('row');
    }

    async openFirstRecord(): Promise<void> {
        // I7: rows matches many — scope before acting
        await this.firstOf(this.rows).click();
    }
}

The generator follows this exact shape, so a hand-written page object and a generated one are indistinguishable in review. That's the point.

Refreshing what the harness knows

The context-builder is a setup agent, not a per-story one. Re-run it when the application gains a module or a role, a release changes navigation or permissions, database access first becomes available, or the other agents keep asking about an area context/ does not cover.

  1. Run /playwright-context-builder and name what changed — "the Reports module is new", "re-walk the read-only role". Named, it runs for that alone.
  2. Answer its checkpoints. It reads the existing baseline and shows differences before overwriting anything a person corrected.
  3. Review what it changed, as you would any draft.

Small drift does not need the agent: when one test fails because a context/ document no longer matches the app, fix the document in the same change as the test.

Onboarding someone new

  1. This page — orientation and agents
  2. SETUP.md, even if the harness is already configured — it explains why each piece exists
  3. TEST-AUTHORING-INVARIANTS.md — eight rules, one page
  4. tests/example.spec.ts — the conventions in working code
  5. First task: add one page object by hand. Faster to understand the Page Factory by wiring one than by reading about it.

Skip the agents until after that. Someone who doesn't know the conventions can't review agent output — and reviewing agent output is most of the job.

Closing a test cycle

  1. Update specs/execution/manual-results.csv with every manual case's real outcome.
  2. Run the suite so the latest results reflect the build being closed.
  3. Retest anything reported fixed, so fixed bugs don't count as blocked coverage.
  4. npm run report:cycle, then decide — with the numbers in front of you.

Retesting a fixed defect

When the tracker shows a defect fixed, fill trackerKey in its defect-log entry and ask /playwright-test-healer to retest. It un-fixmes the test, runs it twice, and either marks the entry verified or restores the fixme and reports that the fix didn't hold.
